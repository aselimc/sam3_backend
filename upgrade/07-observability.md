# 07 — Observability

The system has three signal types — logs, metrics, traces — emitted by both API and worker, collected by an OTel Collector, and consumed by Prometheus + Grafana in the local profile (Loki + Tempo + sampling tiers + SLO burn alerts are added by the enterprise overlay; see [`enterprise/04-observability-at-scale.md`](../enterprise/04-observability-at-scale.md)). SLOs and alert rules below describe the local-profile baseline.

Metric labels include `model_id` and `gpu_class` everywhere they are meaningful; the local profile additionally labels worker metrics with `gpu_index` (0 or 1) so two-GPU dashboards distinguish per-device pressure.

## Log schema

JSON to stderr; loguru on the writer side; Loki on the read side. Every line carries a fixed top-level set of fields so cross-tier correlation works without parsing message text.

```json
{
  "ts": "2026-04-25T10:00:14.871Z",
  "level": "INFO",
  "service": "api" | "worker" | "beat" | "webhook",
  "version": "1.4.2",
  "request_id": "8c8e5f8e-...",
  "trace_id": "7f3c...",
  "span_id":  "9b1d...",
  "tenant_id": "9c3f...",
  "owner_id":  "0e6d...",
  "job_id":    "0e6d...",      // null on API requests with no job
  "msg": "inference done",
  "model_id": "sam3",
  "gpu_class": "a100_40g",
  "duration_ms": 14123,
  "gpu_mem_alloc_mb": 6420
}
```

Rules:

- `request_id` is generated by the API middleware if missing, propagated to the worker via the Celery payload.
- `trace_id` and `span_id` come from OTel; logs without an active span omit them.
- No PII. Image content is never logged. Prompts are logged at DEBUG only and gated by `LOG_PROMPTS=false` in prod.
- Errors include `error_code` plus a single-line `error.summary`; full traceback at DEBUG only.

## Metrics

Exposed via `/metrics` on a sidecar port (`:9100`) — never on the public listener.

| Metric | Type | Labels | Notes |
|---|---|---|---|
| `http_requests_total` | counter | `route`, `method`, `status` | from prometheus-fastapi-instrumentator |
| `http_request_duration_seconds` | histogram | `route`, `method` | P50/P95/P99 panels |
| `auth_events_total` | counter | `kind` (login_ok/login_fail/apikey_used) | |
| `idempotency_replays_total` | counter | `route` | |
| `rate_limit_block_total` | counter | `bucket` | |

### Worker tier

| Metric | Type | Labels | Notes |
|---|---|---|---|

| `worker_batch_size` | histogram | `queue` | actual batch size at flush |

### Broker / queue

| Metric | Type | Labels |
|---|---|---|
| `celery_queue_length` | gauge | `queue` |

`celery_queue_length` is collected by a small `celery-exporter` sidecar that LRANGEs the queue keys.

### DB

`postgres_exporter` defaults plus a dashboard panel for the `idx_jobs_state` partial index hit ratio.

### Storage

CloudWatch / Cloud Monitoring metrics for S3 in prod; MinIO Prometheus endpoint in dev.

## Tracing

OTel SDK auto-instruments FastAPI, SQLAlchemy, redis-py, boto3, requests. Custom spans:

| Span name | Emitted by | Notable attributes |
|---|---|---|
| `api.tasks.submit` | API | `task_type`, `model_id`, `gpu_class` |
| `api.uploads.presign` | API | `byte_length`, `content_type` |
| `worker.run_task` | Worker | `job.id`, `attempt`, `batch.size`, `gpu.mem_used_mb` |
| `worker.adapter.load` | Worker | `model_id`, `cold` (bool) |
| `worker.adapter.infer` | Worker | `batch.size` |
| `worker.s3.fetch` | Worker | `bytes` |
| `worker.s3.upload` | Worker | `bytes`, `n_artifacts` |
| `webhook.dispatch` | Dispatcher | `attempt`, `status` |

Sampling: head-sampled at 10% in prod, 100% in staging. Errors always sampled.

## SLOs

| SLO | Window | Target | Burn-rate alerts |
|---|---|---|---|
| API availability | 30 d | 99.9% (5xx-rate) | Fast (1 h ≥ 14×) + slow (6 h ≥ 6×) |
| Job success rate (post-validation) | 30 d | 99.0% | Fast (1 h ≥ 14×) |
| P95 inference latency `(model_id, gpu_class)` | 7 d | model-specific (e.g. SAM3 on A100-40G ≤ 800 ms for 1024² image, batch 1) | 1 h burn |

Validation errors (4xx) excluded from job success rate; user error must not page on-call. Cancellations excluded from both directions.

Error budget tracked in a Grafana dashboard sourced from a recording rule:

```yaml
- record: job:success_ratio:rate30d
  expr: |
    (sum(rate(worker_jobs_total{outcome="succeeded"}[30d])))
    /
    (sum(rate(worker_jobs_total{outcome=~"succeeded|failed"}[30d])))
```

## Dashboards

Five dashboards, all under `infra/grafana/`.

1. **API health** — RPS by route, P95 latency, 4xx/5xx, rate-limit blocks.
2. **Queue depth** — per-queue length, oldest message age, redelivery rate.
3. **Inference** — P50/P95 by `(model_id, gpu_class)`, batch size distribution, OOM rate, cold-start frequency.
4. **GPU** — `worker_gpu_mem_used_mb`, evictions, warm-pool load state.
5. **Tenants** — top tenants by jobs/min, by GPU-seconds, by failure rate.

## Alerts

Every alert has a runbook URL. Alerts without runbooks fail the lint step.

| Alert | Condition | Severity |
|---|---|---|
| API 5xx burst | rate of 5xx > 1% over 5 m | page |
| Queue stuck | oldest message age > 10 min | page |
| Worker no heartbeats | `rate(worker_heartbeats_total[2m])==0` and pods exist | page |
| OOM storm | `rate(worker_oom_total[10m]) > 0.2` | warn |
| Webhook DLQ growing | undelivered webhooks > 50 for > 30 min | warn |
| DB connection saturation | active conns > 80% pool | warn |
| Redis memory > 80% | from redis exporter | warn |
| Cert expiring | < 14 d | warn |

## Correlation runbook

When investigating a user complaint, the operator path is:

1. Get `request_id` or `job_id` from the user.
2. Loki: `{service=~"api|worker"} | json | request_id="..."` returns every line across the chain.
3. Tempo: `trace_id` from any matching log opens the distributed trace.
4. From the worker span, `job.id` plus the `worker_jobs_total` series at that timestamp confirms outcome and queue.

The presence of `tenant_id` in every line means a single PromQL/LogQL filter scopes any view to one tenant's traffic without cross-contamination.

## Logging volume budget

Default retention: 14 d hot, 90 d cold (S3-backed). Per-line size budget < 2 KB; oversized lines trimmed by the OTel processor with a counter `log_lines_truncated_total{service}`.
